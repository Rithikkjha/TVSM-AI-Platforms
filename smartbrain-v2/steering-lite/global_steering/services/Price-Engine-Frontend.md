## Product Context


# Product: Vehicle Price Engine Frontend

## What This Service Does

This is the frontend application for TVS Motors' Vehicle Price Engine — an internal tool used to define, configure, and manage pricing components and on-road prices (ORP) for vehicles across India. It communicates with a Backend-for-Frontend (BFF) service to perform CRUD operations on pricing data.

The system supports two vehicle categories: **ICE** (Internal Combustion Engine) and **EV** (Electric Vehicle), each with distinct pricing granularity (state-level for ICE, city-level for EV).

## Domain Entities

### Price Component
A configurable pricing rule (e.g., Road Tax, Insurance, Registration Fee) that contributes to a vehicle's on-road price.

- Has a `componentName`, `componentKey`, `componentId`, and `isDeductible` flag
- Scoped by `engineType` (ICE or EV)
- Can be **Global** (applies to all models) or **SKU-specific** (applies to a set of vehicle models)
- Each component has one or more **component definitions** — a combination of region + calculation method
- Lifecycle: Draft → Published (active/inactive toggle)

### Calculation Method
Defines how a price component's value is computed. Three types:

1. **Constant** — A fixed value with a unit of measure (₹ price or percentage)
2. **Parameter** — Slab-based calculation using vehicle attributes (price, weight, engine capacity) with conditional operators (>, <, >=, <=) defining ranges
3. **Custom** — A formula combining other price components using arithmetic operators (+, -)

### Product Price (On-Road Price / ORP)
The final computed price for a vehicle model in a specific region, generated by combining applicable price components.

- Tied to a single vehicle model + region combination
- Contains `exShowroomPrice` and computed component values
- Lifecycle: Generated (draft) → Published

### Vehicle Model
A vehicle SKU with `modelId`, `modelName`, `modelDescription`, and `isNewLaunch` flag. Fetched from the BFF per engine type.

### Region / Location
Hierarchical geography: Country (India) → State (with stateCode) → City (EV only). Pricing is defined at state level for ICE and city level for EV.

## Integrations

### Price Engine BFF (Backend-for-Frontend)
Single backend dependency. Base URL configured via `REACT_APP_PRICE_ENGINE_BFF_BASE_URL`.

Key API groups:
- `/products/vehicle/{engineType}/models` — Fetch vehicle models
- `/regions/{country}/states` — Fetch states for a country
- `/regions/cities?state=...` — Fetch cities for states
- `/product-price-components` — CRUD for price component definitions
- `/product-price-components/publish/{id}` — Publish a draft component
- `/product-price-components/custom/engineType/{type}` — Fetch components available for custom formulas
- `/price-components/{engineType}` — List all price components
- `/price-components/{id}/products` — Get component details with model/region breakdown
- `/on-road-prices` — Generate ORP
- `/on-road-prices/{id}` — Get/update ORP details
- `/on-road-prices/publish/{id}` — Publish ORP
- `/on-road-prices/models/{engineType}` — List ORP status per model

## Business Rules

1. **Engine type determines location granularity**: ICE pricing is at state level; EV pricing is at city level.
2. **Global vs SKU components**: When "Select All Models" is chosen, the component is saved as `isGlobal: true`. Otherwise, specific model IDs are attached.
3. **Draft-first workflow**: Both price components and product prices must be saved as draft before they can be previewed and published.
4. **Custom formula validation**: Formulas are validated using `expr-eval` parser. Only basic arithmetic operators (+, -, *, /) and parentheses are allowed.
5. **Mismatch detection**: Before publishing custom formulas, the system validates that all referenced components exist and are active for every selected model + region combination. Mismatches are surfaced in a popup table.
6. **Slab validation**: For parameter-based calculations, upper limit must be greater than lower limit. Slabs require at minimum: lower limit, conditional operator, component value, and unit of measure.
7. **Component uniqueness**: A component name must be unique within the system per engine type.
8. **Deductible flag**: Components can be marked as deductible, affecting how they contribute to the final on-road price calculation.
9. **Pagination**: All listing APIs support server-side pagination with `rowsPerPage` and `pageNumber` parameters.
10. **Sorting**: Tables support sorting by `updatedOn` (newest/oldest) and filtering by status (active/inactive, available/unavailable).

## Architectural Decisions

1. **HOC-based layout (AppShell)**: Every page is wrapped with `AppShell` which injects navigation, loader state, and toast messaging. This avoids prop drilling for cross-cutting concerns but couples pages to the HOC signature.

2. **Hybrid state management**: Redux Toolkit is used only for globally-shared data (vehicle models, locations). Price component and product price operations use plain async service functions called directly from components — not Redux thunks.

3. **Context for ephemeral cross-page state**: `UserActionContext` holds in-progress form data when navigating between create → preview → back flows, avoiding Redux for transient UI state.

4. **Serializer/Adapter pattern**: API responses are transformed via serializers (response → UI model) and adapters (UI state → API payload). This decouples the UI from backend data shapes.

5. **URL builder functions**: API URLs are constructed in dedicated `api-directory` files rather than inline, centralizing query string logic and making endpoints testable in isolation.

6. **Flat test directory**: All tests live in `src/__tests__/` rather than co-located with source files. Tests cover components, serializers, adapters, enums, and API directories.

7. **No route guards or auth**: The interceptor has commented-out auth token injection. Currently no authentication or authorization is enforced on the frontend.

8. **Environment-based builds**: `env-cmd` switches `.env` files at build time for dev/uat/prod deployments. The only environment variable is the BFF base URL.

## Coding Conventions

### TypeScript
- Strict typing for interfaces and enums; `any` is used in adapters/serializers where API shapes are dynamic
- Enums defined in `src/utils/enum/` — one enum per file
- Interfaces defined in `src/utils/interfaces/` — grouped by domain entity
- Barrel exports via `index.ts` files in most directories

### Naming
- Files: camelCase for utilities/constants (`commonFunctions.ts`), PascalCase for components (`AppRouter.tsx`), kebab-case for domain files (`price-component.ts`)
- Components: PascalCase function components
- Enums: PascalCase enum name, UPPER_SNAKE_CASE values
- Constants: camelCase objects with descriptive keys
- Test files: `{sourceFileName}.test.ts(x)` in `src/__tests__/`

### Component Patterns
- **HOC pattern**: `AppShell` wraps all page components, injecting `navigate`, `location`, `setLoader`, `setCallToastMessage`, `setToastMessage`, `params`
- **Functional components only** — no class components
- **No custom hooks** except `useCityOptions` — most logic lives directly in page components
- **Props via `WithNavigationProps` interface** for all page components

### State Management Patterns
- Redux slices for shared data with `createAsyncThunk` for async fetching
- `dataFetchingStates` enum (`initial`, `loading`, `success`, `rejected`) tracks async operation status
- Direct async function calls (not thunks) for price-component and product-price operations
- Local `useState` for form state within page components
- `useContext(UserActionContext)` for cross-page form data persistence

## Error Handling

### HTTP Layer
- Axios wrapper catches errors in each method (get/post/put/delete), logs to console, and re-throws
- Response interceptor normalizes errors into `Error` objects
- Request interceptor exists but is commented out (auth token injection placeholder)

### Component Level
- Try/catch blocks around async operations in `useEffect` and event handlers
- Errors trigger toast messages via `setCallToastMessage(true)` + `setToastMessage(message)`
- API error messages are extracted from `err.response.data.message` when available, falling back to predefined constants in `labelConstant.ts`
- No global error boundary component

### Validation
- Field validation via `validateFields()` — checks for null, undefined, empty arrays
- Formula validation via `expr-eval` Parser — only allows digits and basic operators
- Slab range validation: upper limit must exceed lower limit
- Mismatch detection: validates component availability across model/region combinations before publish
