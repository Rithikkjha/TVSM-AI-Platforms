# SmartBrain Service Documentation Standard (v1)

One folder per service. Every repo uses the **same files, same headings, same IDs**.

```
<service-id>/
├── service.yaml     # REQUIRED. Machine-readable manifest → graph edges (deterministic)
├── OVERVIEW.md      # REQUIRED. What it is, who owns it, tech stack summary
├── API_SPEC.md      # REQUIRED if the service exposes any API / consumes events
├── DATA_FLOWS.md    # REQUIRED. End-to-end flows this service participates in
├── HLD.md           # High-level design: architecture, decisions, deployment
├── HLC.md           # High-level code: modules, folder layout, core workflows in code
└── LLD.md           # Low-level design: schemas, classes, algorithms, edge cases
```

## Why two layers

| Layer | Consumer | Purpose |
|---|---|---|
| `service.yaml` | Ingestion → Neo4j | Exact edges: who calls whom, who publishes/subscribes what, which DB, which env vars. No LLM guessing. |
| `*.md` | Chunker → Qdrant/BM25 | Narrative answers: why, how, what happens on failure. Fixed headings = consistent chunk tags. |

If a fact is in `service.yaml`, the markdown may explain it but must not contradict it. `service.yaml` wins.

## Hard rules

1. **Canonical IDs.** Every service is referenced by its `service_id` (kebab-case, = repo name, e.g. `payment-service`). Never "PaymentService", "Payment Svc", "payments". Unknown/unregistered targets use `external:<name>` (e.g. `external:juspay`).
2. **Fixed headings.** Keep every `##` heading from the templates, in order. If a section doesn't apply write `N/A — <reason>`. Never delete headings.
3. **Self-contained sections.** Each `##` section should name the service in its first sentence. Chunks are retrieved alone.
4. **No secrets.** Env vars list name, purpose, and where the value comes from. Never values.
5. **Provenance.** Each edge in `service.yaml` carries `source: code | manual | inferred`. `inferred` = generated by AI, unverified.
6. **Front-matter on every .md** (see templates): `service_id`, `doc_type`, `last_reviewed`.

## Questions this standard must answer

- What does X do, who owns it, what stack? → OVERVIEW + service.yaml
- What does X depend on / what depends on X? → service.yaml `outbound` / `inbound` (+ reverse lookup)
- If X goes down, what breaks? → graph traversal over `inbound` with `criticality`
- How does data flow for "booking → payment → confirmation"? → service.yaml `flows` + DATA_FLOWS.md
- Which services touch table/topic/env var Y? → service.yaml `data_stores`, `events`, `config`
- Why was it built this way? → HLD.md decisions
- Where in the code does Z happen? → HLC.md / LLD.md
